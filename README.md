# A股 AI 智能选股系统（v1.0 冻结版）

基于 `E:\星空系统\股票系统\` 下多个开源项目重构的 A 股智能选股与复盘系统。

> **v1.0 自 2026-09-24 起冻结并投入使用。** 冻结期至 2026-12-31，期内只修 bug、
> 只做数据源故障应急与风险类硬约束，**不调参、不加因子、不换口径**。
> 完整契约（含验收目标与停止规则）见 [`config/settings.yaml`](config/settings.yaml) 文件头。

## 决策依据是什么（重要）

| 链路 | 角色 | 可实现口径下的实测 |
|---|---|---|
| **影子模块**（涨停基因 + 缩量不破位） | **唯一决策依据** | 日度聚类超额 **+0.667%（t=5.62）**，观察期选参 → 验证期 t=3.56 |
| 主链路（8 策略 → 评分 → 配额） | **降级为信号观察池**，照常运行 | 超额 **+0.011%（t=0.09）** = 无 alpha |

主链路不再作为投资依据，但它仍在每日运行 —— 它是数据积累、复盘、报告的基础设施。
判据是回测裁判口径从「买入日 `close/open−1`」（A 股 T+1 下**不可实现**）换成
可实现口径后得出的（见第 13 章）。

- 技术栈：Python 3.11 + DuckDB + Parquet + FastAPI + 单页 ECharts 前端 + DeepSeek（可选）
- 数据源：**同花顺**（日线整库导出 / 涨停池 / 炸板池 / 龙虎榜 / 集合竞价 / 财务三表 / 盘中快照）
  + **akshare**（股票列表 / 交易日历 / 指数日线），后三者同花顺无对应端点
- 数据复现：本仓库**只含代码与配置**，`data/`（约 4.6 GB）不入库 ——
  数据来源与从零复现步骤见 **[`config/DATA_SOURCES.md`](config/DATA_SOURCES.md)**

## 一、它现在能做什么

一条命令完成「补数 → 因子 → 市场状态 → 选股 → 评分 → 报告 → 复盘」全链路：

```
python -m astock.cli daily
```

输出：

| 产物 | 位置 | 说明 |
|---|---|---|
| 控制台摘要 | stdout | 市场状态 + 三档候选（总名额 15，按市场状态权重分配） |
| Markdown 报告 | `data/reports/report_<日期>.md` | **影子信号候选**（决策依据）、昨日回顾、主链路候选（观察池）、推荐逻辑、评分拆解 |
| 结构化结果 | `data/reports/report_<日期>.json` | 供 API 与前端消费 |
| 影子信号 | DuckDB `ads_shadow_pick` | **决策依据**：涨停基因 + 缩量不破位，每日落库并自动结算收益 |
| 主链路推荐 | DuckDB `ads_recommend` | 8 策略 + 评分 + 配额的输出，现为**信号观察池** |
| 复盘记录 | DuckDB `ads_review` | 次日自动回填 |

盘中决策（14:00，盘后链路拿不到当天截面）：

```bat
python -m astock.cli snapshot --slot 14:00
```

采集全市场盘中快照（约 40 秒），结果自动关联进报告 —— 影子候选的表格会多出
「快照现价 / 快照涨幅 / 快照量比 / 状态（可买·放弃）」几列，直接回答
「此刻还能不能按信号买」。

Web 界面（市场宽度趋势、涨跌停生态、候选股明细、复盘统计）：

```
python -m astock.cli serve
# 浏览器打开 http://127.0.0.1:8000
```

## 二、快速开始

### 1. 环境（已完成，无需重做）

已创建 conda 环境 `astock`（Python 3.11），依赖全部安装完毕。

如需在新机器重建：

```bat
scripts\setup_env.bat
```

> 建议固定使用 Python 3.11（`requirements.txt` 中的部分依赖在新版本上兼容性未验证）。

密钥配置（**同花顺 Key 必需**：日线、涨停池、财务、盘中快照全靠它）：

```bat
copy .env.example .env
::   编辑 .env，填入 HITHINK_FINANCE_API_KEY（必需）与 DEEPSEEK_API_KEY（可选，AI 报告用）
```

`.env` 已被 `.gitignore` 排除，不会进入版本库。

### 2. 初始化数据库

```bat
D:\miniconda3\envs\astock\python.exe -m astock.cli initdb
```

### 3. 回填历史数据（首次执行一次）

```bat
:: 日线全历史：同花顺 10 年整库导出，1 次请求、分钟级（推荐）
python -m astock.cli dump-daily --days 3650

:: 指数日线（akshare）：市场状态识别的动量维度需要
python -m astock.cli index --years 2

:: 涨停池 / 炸板池（同花顺，限流 15 次/分钟，1 年约 17 分钟）
python -m astock.cli limit-pool --years 1

:: 龙虎榜
python -m astock.cli dragon-tiger --years 1

:: 行业映射 + 板块强度
python -m astock.cli sector
python -m astock.cli sector-strength --all

:: 财务（价值档输入；全市场约 17 小时，可中断续传，建议夜间跑）
python -m astock.cli finance --all

:: 派生表
python -m astock.cli factor
python -m astock.cli regime
```

> **完整的从零复现步骤（含每张表的来源、自检预期值、历史深度限制）见
> [`config/DATA_SOURCES.md`](config/DATA_SOURCES.md)。**
>
> 注意 `backfill` 命令是「逐只拉取」路径（现走 akshare，5000+ 只、小时级），
> 只在需要按代码补特定区间时使用；**首次建库请用 `dump-daily`**。
> `data/` 目录不入库，换机器必须按上述步骤重建。

#### 怎么查看回填进度

**采集正在运行时**（数据库被独占）：

```bat
python scripts\monitor.py
```

输出包含：当前批次、进度条、已入库行数、失败数、剩余时间估算、数据源限流告警、
以及「采集任务是否真的在运行」的结论（通过读取进程命令行判断，不靠猜日志）。

**采集已停止时**（数据库空闲，数字最准）：

```bat
python -m astock.cli status
```

输出 `coverage` 字段即覆盖率，`stocks_covered` / `stocks_total` 为具体只数。

若主库正被占用，`status` **会自动降级**到展示层快照并打印占用进程的 PID，不会直接报错卡住。
也可以强制只读快照（任何任务运行期间都能用）：

```bat
python -m astock.cli status --snapshot
```

**两个命令都在** `data\logs\` 下对应的日志文件：

| 文件 | 内容 |
|---|---|
| `data\logs\astock.log` | 结构化日志（UTF-8，含所有模块的 INFO/DEBUG） |
| `data\logs\backfill.log` | 回填任务的 stdout（中文可能因控制台代码页而乱码） |

**耗时对比（口径已变更，务必注意）**：

| 路径 | 命令 | 耗时 |
|---|---|---|
| **同花顺整库导出（现行）** | `dump-daily --days 3650` | **分钟级**（1 次请求下载全市场 10 年日 K） |
| 逐只拉取（遗留） | `backfill --years 2 --workers 4` | 小时级（5559 只 × 单只中位 1.67 秒，4 进程约 1 小时） |

每日增量走整库导出（见下），逐只路径只在按代码补数时使用：

```bat
python -m astock.cli backfill --years 2 --codes 600519,000001
```

**中断无所谓**：两种路径都可重跑续传，已入库的股票会自动跳过。

### 4. 每日流程

```bat
python -m astock.cli daily
```

### 5. 查看界面

```bat
scripts\run_serve.bat
```

浏览器打开 `http://127.0.0.1:8000`。

> **重要说明（计算层与展示层是分开的）**
> DuckDB 对数据库文件是**独占锁**，服务与采集无法同时持有主库。
> 因此 Web 服务只读 `data/serving/*.parquet` 快照，**完全不碰主库**。
> 结果是：**回填 5500 只股票的同时，界面照常可用**。
> 界面显示的是「上一次 daily 导出的快照」，想看最新数据就再跑一次 `daily`
> （或单独执行 `python -m astock.cli export` 仅刷新快照，不重算选股）。

## 五、数据层

### 表结构

| 表 | 用途 |
|---|---|
| `dim_stock` | 股票维度（名称、板块、上市日期、ST、状态） |
| `trade_calendar` | 交易日历 |
| `dwd_daily_bar` | 日 K 线（核心明细） |
| `dwd_index_bar` | 指数日线 |
| `dws_feature` | 因子宽表（全部由 SQL 窗口函数计算） |
| `dws_market_regime` | 每日市场状态快照 |
| `ads_recommend` | 推荐记录 |
| `ads_review` | 复盘记录 |
| `sys_collect_state` | 采集游标（断点续传核心） |
| `sys_llm_usage` | LLM token 消耗审计 |

### 针对「电脑不保证 24 小时开机」的设计

1. **幂等写入**：所有写入按主键 `INSERT OR REPLACE`，重复跑不产生脏数据。
2. **断点续传**：以「本地最新日期」为游标，中断后重跑自动只补缺失部分。
3. **自动补数**：`daily` 启动时比对交易日历与本地数据，若有缺口自动逐日补齐。
4. **失败不误判**：采集失败与「该股确实无数据」严格区分 —— 失败不会写 `EMPTY` 标记，下次还会重试。
5. **冷热分离**：超过 `storage.hot_days` 的明细可归档为 Parquet（`Storage.archive_parquet`）。

## 六、策略清单

### 波段档（3~20 日）

| 策略 | 来源 | 条件 |
|---|---|---|
| 海龟突破 | 移植 Sequoia-X | 20 日新高 + 成交额过亿 + 实体阳线真涨（防诱多） |
| 均线放量金叉 | 移植 Sequoia-X | MA5 上穿 MA20 + 量能 > 20 日均量 1.5 倍 |
| RPS 相对强度突破 | 移植 Sequoia-X | 120 日 RPS ≥ 90 + 接近 120 日高点 |
| 高窄旗形整理 | 移植 Sequoia-X | 40 日强动量 + 10 日极度收敛 + 缩量 + 高位抗跌 |
| 上升趋势跌停反包 | 移植 Sequoia-X | MA20 > MA60 + 今日放量跌停（错杀） |

### 短线档（1~3 日）

| 策略 | 来源 | 条件 |
|---|---|---|
| 涨停洗盘回踩 | 移植 Sequoia-X | 昨日涨停 + 今日放量收阴 + 不破昨收 |
| 次新股异动 | 新增 | 上市 ≤ 120 日 + 换手 ≥ 15% + 放量 + 涨幅 ≥ 3% |

> 短线档定位为**盘后生成次日观察池**，不做盘中实时信号（受限于机器不常开 + 免费源分钟数据不稳定）。

### 价值档（1 月~1 年）

| 策略 | 来源 | 条件 |
|---|---|---|
| 长期均线多头 | 新增（Phase 1 趋势代理） | MA20 > MA60 > MA120 + 未有效跌破 MA20 |

> **基本面已接入**（同花顺财务三表 → `dws_finance_metrics`）：价值档的因子分中混入
> 40% 基本面分（`scoring.fundamental.value_weight`）。但实测它换掉了档内 **78% 的名单**
> 却没带来业绩改善（在旧口径下测，且该口径本身不可信）—— 冻结期内**不再调整**，
> 待影子模块验收后再统一重估。

### 与 Sequoia-X 的差异

| 维度 | Sequoia-X | 本系统 |
|---|---|---|
| 计算方式 | 逐股 Python 循环 | **全市场 SQL 向量化**（快一个数量级） |
| 输出 | 裸代码列表 | 带分值 + 推荐理由的 Candidate |
| 存储 | SQLite | DuckDB + Parquet |
| 选股池 | 全市场 | 全 A 股 + 风险过滤，**保留次新股**（数据不足时降级而非剔除） |
| 策略参数 | 硬编码 | 全部外置到 `settings.yaml` |

## 七、市场状态识别

移植 market-breadth 的「宽度」思想（站上均线的股票占比），扩展为五状态：

| 状态 | 判定特征 | 主推档位（已按回测校准） |
|---|---|---|
| 趋势行情 | MA60 上方占比 ≥ 55% + 指数 20 日不跌 | 短线（0.50） |
| 情绪高潮 | 涨停 ≥ 80 家 + 炸板率 ≤ 20% | 短线（0.70） |
| 情绪退潮 | 跌停 ≥ 30 家，或炸板率 ≥ 45%，或涨停家数萎缩且宽度走弱 | 短线（0.55） |
| 震荡行情 | MA20 宽度在 35%~55% 之间 | 短线（0.55） |
| 事件驱动 | 单一板块涨停占比 > 30%（Phase 2 接入板块数据后启用） | 短线（0.60） |

输出**三档权重**，直接调制策略评分的「市场适配分」，实现「先判断环境、再选择策略」。

> ⚠️ **这套权重是实测校准的结果，不是直觉。**
> 最初的配置写的是「趋势行情加码波段（0.7）、情绪退潮防守价值（0.8）」，
> 但 485 个交易日的逐日回放证明这是**反的**：短线档在全部 5 种市场状态下
> T+1 平均收益都最高（趋势期 +1.05% vs 波段 +0.19%；退潮期 +1.69% vs 价值 +0.58%）。
> 校准依据与完整数据见 `config/settings.yaml` 中 `market_regime.tier_weights` 的注释，
> 随时可用 `python scripts\regime_matrix.py` 重新核算。

## 七点五、行业与板块强度

A股的收益很大程度由板块效应驱动。本系统接入了行业数据，但**采用了与直觉不同的做法**。

### 关键设计：只从接口拿「个股→行业」映射，板块强度自己算

免费板块接口的实测情况：东财被拦、申万**时好时坏**（同一天先成功 13/31，几分钟后连行业列表都失败）、
新浪稳定但只覆盖 48.9%（不含新股）、同花顺本机版本无成分接口。

接口快照还有两个致命局限：**只有当日、没有历史**，因此无法回测「板块效应是否有效」。

所以：

| 做什么 | 谁来做 | 为什么 |
|---|---|---|
| 个股 → 行业 映射 | 接口多源互补 | 相对静态的维度数据 |
| 板块日度强度 | **本地日线自算** | 可回填历史、可回测、不受接口稳定性影响 |

```bat
python -m astock.cli sector --refresh-primary   :: 切换主用来源后刷新标签
python -m astock.cli sector                     :: 同步映射（约 3 分钟）
python -m astock.cli sector --top 15            :: 顺便看当日板块强度排行
python -m astock.cli sector-strength            :: 由本地日线算板块强度（可回填）
```

### 实测结果

- **映射覆盖率 99.4%**（5523/5559）：申万 87% + 新浪 54%，两者互补；
  **推荐池覆盖率 短线/波段 100%、价值 91.7%**
- 申万成分接口顺带回填了 **4851 条基本面数据**（ROE/净利润增速/营收增速/PE/PB）——
  本来排在后续计划里的价值档数据，顺手就拿到了
- 板块强度回填了 **486 个交易日 × 两套分类体系**

### 一个必须如实指出的发现：板块动量很弱，且集中度到极值时会反转

用 486 天历史自算的板块强度做了两次检验：

**① 板块层面**：强度最高的板块，次日平均 +0.212%；最低的 +0.125%。有正向但差距仅 0.09pp，
且分位单调性不完美。

**② 个股层面**（更关键）：所属板块强度 ≥80 的股票次日 +0.218%，全市场基准 +0.152%，
超额 **+0.066pp**。但各分位的**胜率几乎相同**（48.7%~49.9%）、**中位收益全为 0** ——
这是典型的**赔率型弱信号**，靠极端值拉动，不是胜率型。

**③ 意外反转**：单个板块涨停家数占全市场 **22% 以上**（"事件驱动"状态）时，
该板块**次日平均 −0.10%**，而其它状态下的最强板块都是 +0.17%~+0.28% ——
**集中度到极值更像是分歧前兆，而非主线延续**。

### 因此的三个决策

1. **板块强度不参与打分**，只用于展示与归因（报告里显示"所属板块 + 当日强度"）
2. `event`（事件驱动）状态的权重从 `{short:0.60}` 回调到 `{short:0.50}`，
   因为"虹吸=可追"的假设被数据否定
3. `event` 状态阈值从拍脑袋的 30% **校准为实测的 22%**——原值 486 天里**从未触发过**，
   等于该状态形同虚设；22% 触发 47 天（9.7%），样本足以回测

> 后续若要利用板块信号，更可能有效的方向是「板块强度作为**过滤条件**」
> （剔除板块弱的票）而非加权；或反过来做**板块强度反转**（买弱卖强），
> 但这需要回测验证，见 TODO。

## 八、主链路的评分与配额（现为信号观察池）

> **定位说明**：本节描述的链路在可实现口径下超额 **+0.011%（t=0.09）**，即无 alpha，
> **已降级为信号观察池**，不再作为投资依据（决策依据见 8.5 影子模块）。
> 之所以保留并继续运行：它是数据积累、复盘归因与报告的基础设施。

### 融合公式

```
最终分 = 0.53 × 策略强度 + 0.47 × 因子分 − 风险扣分        （权重两两归一化）
```

- **策略强度**：条件满足程度（连续变量，不是布尔），0~100
- **因子分**：量能 30% + 相对强度 30% + 动量 25% + 位置 15%，全市场分位数标准化
- **风险扣分**：ST、流动性不足、波动过大、60 日高位追高、次新股风险
- **市场适配项已移除**：它在同一档位内是常数（只取决于所属档位），档内排序时是常数偏移，
  **从未影响过任何一次选股决策**。档位权重的作用改由「名额分配」承担（见下）
- 价值档额外混入 40% 基本面分（`scoring.fundamental.value_weight`）；实测它换掉了
  **78% 的档内名单**但业绩无显著改善，暂保留观察

每只候选都保存**评分拆解**，用于回答「为什么推荐它」。

### 名额分配（配额制）

总名额 **15 只**按市场状态权重分配到三档（最大余数法，总和恰为 15），短线档封顶 5 只，
某档候选不足时空缺名额**按权重转给其它档**。

### 复盘口径

- 推荐在数据日盘后生成，计划在**次一交易日开盘买入**
- 记录：当日收益、最大涨幅、最大回撤、持有 3 日收益
- **裁判口径**：`ret_exit_d1c`（买入次日收盘卖 —— T+1 下最早合法卖点）；
  `ret1`（买入当日 `close/open − 1`）**不可实现**，仅作诊断字段保留

## 八点五、影子信号（v1.0 决策依据）

定位：**独立于主评分体系** —— 只落库、结算、统计，不参与主链路选股，两边互不污染
（主链路的裁判口径曾长期错误，混在一起会导致两边都无法归因）。

### 信号定义

| 条件 | 定义 |
|---|---|
| 涨停基因 | 过去 28 自然日内有涨停，且距上次涨停 ≤ 10 天 |
| 缩量 | 当日成交量 < 前 5 日均量的 70% |
| 不破位 | 收盘 ≥ 前 5 日均价的 98% |
| 买入 / 卖出 | 整理期**市价**买入（非涨停价）→ 持有 D+1 / D+3 / D+5 收盘 |

### 为什么是这三个条件（而不是「洗盘回踩」的直觉）

实测四组对照（同一样本期内）：

| 形态 | 样本 | 次日涨停率 | 次日 | 3日 | 5日 |
|---|---|---|---|---|---|
| 全市场（无条件基准） | 192 万 | 2.05% | +0.136% | +0.353% | +0.562% |
| 仅涨停基因 | — | 6.66% | -0.111% | -0.248% | -0.379% |
| **基因 + 缩量 + 不破位** | 9187 | **8.29%** | **+0.554%** | **+0.904%** | **+0.822%** |
| 基因 + 缩量 + 回踩破位 | — | 3.58% | -0.294% | -0.396% | -0.316% |

两条关键结论：

1. **「涨停基因」单独是负收益**（-0.111%）—— 它是公开且已被定价的信息；
   必须叠加「缩量 + 不破位」才转为正期望。
2. **「缩量整理」有效，「缩量回踩」有害**：后者超额 -0.249%，**t=-2.94（显著为负）**。
   ⇒ 「不破位」条件**不可**改成「回踩」。主链路里的 `limit_up_shakeout`
   （涨停洗盘回踩）用的是「**放量 2 倍**」，与数据指向正好相反，
   这可能是它在事件驱动状态下 t=-2.05（显著更差）的原因。

### 检验结论（240 个交易日 / 9187 笔）

- 次日涨停率 **9.2%**（全市场 2.05% → **4.5 倍**）
- 可实现收益：次日 **+0.559%** / 3日 **+0.892%**
- 日度聚类超额 **+0.667%（t=5.62）**
- **观察期选参 → 验证期 +0.697%（t=3.56）** ← 本项目第一个通过**真正样本外**的信号
- 6 个市场状态**全部为正**（与 style_matrix「状态×规则绑定无正向依据」形成对照）

### ⚠️ 三条必须记住的限制

1. **收益 100% 来自尾部**：剔除命中涨停的 9.17% 后，其余持仓超额 **-0.440%（t=-5.54）**。
   这是"彩票型"结构，靠每日 30~40 只的**分散化**才成为正期望 —— **绝不可重仓单票**。
2. **样本只有 1 年**（`dwd_limit_up` 只覆盖 2025-09-23 起）→ **无跨周期检验**。
3. **年化 +89%（扣成本后）不可信**，更可能是样本期特性 → **不可据此加大仓位**。

### 每日执行（已自动化）

`daily` 流程中排在「复盘」之后、「报告」之前：`shadow settle`（结算收益）→ `shadow build`（生成次日候选）。
报告第二板块「影子信号候选」即由此产出；若当日 14:00 采集过快照，表格会自动附带
「快照现价 / 快照涨幅 / 快照量比 / 状态（可买·放弃）」实况列。

```bat
python -m astock.cli shadow status                              :: 看成绩
python -m astock.cli shadow backfill --from 2025-09-24 --to 2026-09-22 && python -m astock.cli shadow settle
```

## 九、AI 与 Token 成本控制

参考 caveman 的压缩思路，落地为六条规则（见 `astock/llm/`）：

1. 只对当日 Top-N 候选调用 LLM，全市场扫描全在本地完成
2. 输入只传「已算好的指标」，不传原始 K 线序列（输入 token 降幅最大的一环）
3. 强制 JSON 结构化短输出，禁止自然语言段落
4. 每个字段长度硬限制，禁止铺垫与总结句
5. 每日 token 预算护栏，超限自动降级为本地模板报告
6. 消耗量落库 `sys_llm_usage`，可随时审计

**默认关闭 LLM**，纯本地模板也能生成完整报告。启用步骤：

1. 复制 `.env.example` 为 `.env`，填入 `DEEPSEEK_API_KEY`
2. `.env` 中设 `LLM_ENABLED=true`
3. 运行 `python -m astock.cli daily --llm`

预估成本：每日 15 只候选 × 约 1.8K token ≈ **0.05~0.1 元/天**。

## 十、定时任务与备份

以管理员身份运行：

```bat
scripts\register_task.bat
```

会注册三个任务：

| 任务名 | 时间 | 作用 |
|---|---|---|
| `AStockAI_Snapshot` | 每交易日 **14:00** | 采集全市场盘中快照 → 自动重建报告（附带「此刻能否买入」实况） |
| `AStockAI_Daily` | 每交易日 **18:30** | 每日全流程（补数 → 因子 → 市场状态 → 选股 → 影子信号 → AI 报告 → 复盘） |
| `AStockAI_Backup` | 每周日 20:00 | 数据备份 |

**为什么 14:00 必须独立成任务**：`daily` 依赖 `data.data_ready_time`（`16:00`）守卫，
14:00 运行时守卫会**主动回退到上一交易日**，产出的只是「昨天的数据日 + 今天（已错过开盘）
的计划日」。盘中决策要的是「当天此刻」的截面，只能走独立链路。
这也是**唯一有时效性**的一步：免费源不提供历史盘中数据，晚一天记录就永远少一天样本。

**为什么是 18:30**：配置项 `data.data_ready_time`（默认 `16:00`）规定了当日行情视为「完整可用」的时间点。
早于该时间运行 `daily` / `backfill` 时，系统**只处理到上一个交易日** —— 因为收盘前拉到的 K 线不是完整日线，
而一旦入库就会成为「本地最新日期」游标，后续补数会直接跳过，**错误数据会被永久保留**。

**为什么不用 `schtasks` 命令行**：`schtasks /Create` 无法设置 `StartWhenAvailable`（错过计划时间后补跑）。
本机不保证 24 小时开机，18:30 若关机或休眠，任务会被直接跳过、当天什么都没有。
`register_task.ps1` 用 `New-ScheduledTaskSettingsSet -StartWhenAvailable` 解决这个问题，
并同时设置「使用电池也运行」「不因切换电源状态而停止」「超时 3 小时」「不重复叠加实例」。

定时任务失败时，`run_daily.bat` 会：
1. 把 Python 的退出码**透传出去**（否则任务计划程序永远显示「上次结果 0」，失败被静默吞掉）；
2. 在 `data/logs/LAST_DAILY_FAILED.txt` 留下标记，`python scripts\monitor.py` 会把它顶到最上方显示。

### 数据备份

```bat
scripts\backup_data.bat                          :: 备份到 data\backups\
scripts\backup_data.bat --dest E:\astock_backup   :: 备份到另一个盘（推荐）
scripts\backup_data.bat --list                    :: 查看已有备份
```

备份内容：主库 `astock.duckdb`、`skills/`、`config/settings.yaml`、`data/reports/`、`data/backtest/`、`data/serving/`。
**刻意排除** `.env`（含 API Key，不随备份扩散）与 `data/logs/`（体积大、价值低）。

两个关键设计：

1. **主库被占用时拒绝备份**。DuckDB 是单文件存储，有写进程在跑时直接复制会得到
   「看似完整、实际损坏」的副本 —— 这种备份比没有备份更危险，因为它只会在真正需要恢复时才暴露问题。
2. **备份后校验副本**。会打开副本查一次日线行数并与源库比对，不一致就删除本次备份并报错。
   不做校验的话，备份可能长期是个坏文件而无人知晓。

> ⚠️ 默认备份到 `data\backups\`，与主库**同一块磁盘**，只能防误删、防不了磁盘损坏。
> 定期加 `--dest` 指到移动硬盘或网盘才是真的防灾。

## 十一、常见问题

**Q: 全市场回填太慢？**
不要用 `backfill`（逐只拉取，小时级）——首次建库用 `dump-daily --days 3650`（同花顺整库导出，**分钟级**）。

**Q: 提示某只股票无数据，但它是正常股票？**
用 `python -m astock.cli check` 查看。未覆盖的绝大多数是**已退市股**（正常）。仍显示上市却无数据的，用 `backfill --codes <代码>` 单独补。

**Q: 为什么短线档经常没有候选？**
短线策略条件较严（需要昨日涨停 + 今日洗盘）。另请注意：主链路已降级为信号观察池，
真正要执行的是**影子信号**（日均 30~40 只，见第 8.5 节）。

**Q: 报告里的「影子信号候选」为什么有时没有 14:00 实况列？**
说明生成报告时计划交易日的快照还不存在（18:30 生成时属正常）。14:00 采集快照后
`run_snapshot.bat` 会自动重建报告，那时实况列就有了。

**Q: 影子信号为什么强调「等权分散」？**
它的收益 100% 来自约 9% 命中涨停的尾部，**单票期望为负** —— 靠分散才成为正期望。
重仓少数几只，等于把彩票型结构变成赌博。

**Q: 能改成自动下单吗？**
本系统定位为「AI 研究员 + 多策略选股 + 复盘进化」，不含交易执行，避免误操作风险。

**Q: 想换 PostgreSQL？**
只需替换 `astock/storage/db.py` 中的 `Storage` 实现，业务层不接触数据库 API，无需改动其它代码。

## 十二、数据源现状与故障处理

### 0. 当前数据源（2026-09-24 收敛后）

| 来源 | 负责 | 说明 |
|---|---|---|
| **同花顺** | 日线（整库导出）/ 涨停池 / 炸板池 / 龙虎榜 / 集合竞价 / 财务三表 / 盘中快照 | 需 `HITHINK_FINANCE_API_KEY`；限流 **15 次/分钟**（客户端固定 4.2 秒间隔） |
| **akshare** | 股票列表 / 交易日历 / 指数日线 | 免费；同花顺无这三个端点（探测均 404） |

```yaml
data:
  primary_source: akshare
  source_fallback: []        # 不再有降级源：日线唯一来源是同花顺整库导出
```

**已下线的源**：`baostock`（socket 连接脆弱、登录过频会被拉黑）、`adata`（几乎未使用）。
日线由此前的「逐只拉取」改为「整库导出」，耗时从小时级降到分钟级。

### 1. 同花顺报 `code=1002 / Unknown thscode`

最常见的原因**不是**限流、也不是数量超限，而是**请求里混进了已退市股票代码**
（它不在上游的存续列表里），整个批次都会失败。代码已统一从
`dim_stock WHERE out_date IS NULL` 取代码。

> 这个报错曾导致一次错误结论（「同花顺快照批量上限只有 2 只」），真实原因是请求里
> 混进了已退市的 `000003.SZ`。排查同类问题先确认代码是否存续。

### 2. 代理方向问题（两个相反的场景，别混淆）

国内数据源**必须直连**（经系统代理反而不稳）：

```yaml
data:
  bypass_proxy: true
```

而推送 GitHub **必须走代理**（直连时 TLS 会被重置）：

```bat
git config http.proxy http://127.0.0.1:7897
git config https.proxy http://127.0.0.1:7897
```

### 3. 采集报「整批 100% 失败」

上游限流或网络中断。脚本会中止并提示，**不会**把失败的股票标记成「无数据」，
恢复后重跑即可补齐。

排查工具：

```bat
python scripts\probe_hithink.py       :: 同花顺核心接口连通性
python scripts\probe_network.py       :: 各行情站点是否可达
python scripts\monitor.py             :: 后台任务进度与存活状态
python -m astock.cli check            :: 区分「真退市」与「采集失败」
```

### 4. 历史记录：baostock「黑名单用户」（该源已下线，仅作参考）

```
login failed! baostock 登录失败: 黑名单用户，请与管理员联系
```

早期实现并行采集时每只股票 `login` + `logout`，800 只即 1600 次登录，服务端直接封禁。
后改为「每进程只登录一次」，但该源最终仍被移除（连接脆弱、易被拉黑）。

### 5. 历史记录：akshare 通道三层降级（现仅用于基础三件套）

| 顺序 | 站点 | 实测表现 |
|---|---|---|
| 1 | 新浪 `stock_zh_a_daily` | **最稳**，约 0.5 秒/只 |
| 2 | 腾讯 `stock_zh_a_hist_tx` | 可用，约 1.3 秒/只 |
| 3 | 东财 `stock_zh_a_hist` | 字段最全，但限流时直接断连 |

> 新浪/腾讯**不提供昨收**，代码用前一行收盘价推算 `preclose` 与 `pct_chg`；
> 新浪的 `turnover` 是**小数比例**（0.00196），已统一 ×100 转为百分数。

## 十三、样本外验证（回测）

用来回答一个关键问题：**这些策略到底赚不赚钱，还是只是看起来合理？**

```bat
scripts\run_backtest.bat                    :: 全区间回放
scripts\run_backtest.bat --months 6         :: 只回放最近 6 个月
scripts\run_backtest.bat --tiers swing      :: 只验证波段档
scripts\run_backtest.bat --list             :: 查看历史回测运行
```

等价命令：`python -m astock.cli backtest --months 6 --top-n 5`

### 回测口径（决定了结果是否可信）

| 环节 | 处理方式 | 为什么这样做 |
|---|---|---|
| **裁判口径** | **`ret_exit_d1c`** = 买入次日收盘卖 | 这是 T+1 制度下**最早合法**的卖点之一，唯一能指导实盘 |
| 最早合法卖点 | `ret_exit_d1o` = 买入**次日开盘**卖 | 更早的卖点在制度上不存在 |
| ⚠️ 不可实现口径 | `ret1` = 买入当日 `close/open − 1` | 买入当日不能卖（T+1）。它系统性高估收益，**仅作诊断** |
| 选股数据 | 只用当日及之前的数据 | 因子表按日存储，天然无未来函数 |
| 买入价 | **次一交易日开盘价** | 用当日收盘价买入是做不到的 |
| 股票池 | 按当日截面过滤 | 用今天的成交额门槛筛两年前的股票是作弊 |
| 退市股 | 按当时 `out_date` 判断 | 用「今天还活着」反推会产生**幸存者偏差** |
| 市场状态 | 取当日快照 | 权重也必须 as-of |
| 稳定性 | 切分观察期 / 验证期 | 识别「前半段灵、后半段废」的伪参数 |

> **为什么口径如此重要（v1.0 的关键发现）**：改为可实现口径后，主链路的
> 「显著超额 +0.310%（t=2.90）」直接归零为 **+0.011%（t=0.09）**。
> 此前所有基于 `ret1` 的调参结论（配额制、短线档上限、入场成本过滤、基本面接入）
> **全部作废重看** —— 它们都在优化一个不可实现的目标。

### 输出内容

- **整体表现**：可实现口径的胜率、平均收益、盈亏比、持有 3/5/10 日收益、最大涨幅/回撤
- **对照展示**：可实现口径与诊断口径（`ret1`）并排，防止再次出现「换口径结论反转」
- **分档位 / 分策略**：定位哪些策略真的有效、哪些该淘汰
- **分市场状态**：验证「趋势行情推波段、情绪高潮推短线」是否成立
- **多策略共振**：验证「多策略同时命中更好」这个直觉是不是伪信号
- **观察期 vs 验证期 / 按月**：判断参数是稳健还是偶然

产物落在 `data/backtest/`：

| 文件 | 内容 |
|---|---|
| `backtest_<run_id>.md` | 完整报告（含结论与建议） |
| `backtest_<run_id>.csv` | 每条信号的明细，可自行用 Excel 做二次分析 |

### ⚠️ 调参已被冻结（v1.0 契约）

**冻结期内不做任何参数调整。** 依据：

1. 487 天数据上跑过的 7 轮回测（配额制、短线上限、基本面、入场过滤……），
   在诚实裁判下**全部落在噪声范围内**（改什么都没用）。
2. 台面上没有「某状态适合某档位」的证据（`dws_style_matrix` 42 个格子 0 个显著更好）。
3. 真正的改进来自**引入新信息源**（影子信号就是这条路），而不是继续加工已有信息。

若将来解冻，最低要求：**观察期选参 → 验证期检验**（影子模块用的就是这套：
观察期 t=4.81 → 验证期 t=3.56），并且样本数 < 30 的子组不下结论。

## 十四、策略 Skill 库

把每个策略落成**独立目录**，形成可持续迭代的策略资产（目录规范参考 UZI-Skill）。

```bat
python -m astock.cli skills list              :: 列出全部策略与判定
python -m astock.cli skills show turtle_trade :: 查看单个策略完整档案
python -m astock.cli skills sync              :: 重新落盘（含参数变更记版本）
python -m astock.cli skills stats             :: 刷新历史成功率
```

### 目录结构

```
skills/
├── README.md                 索引（人读，含判定汇总表）
├── registry.json             索引（程序读：前端 / API / Agent 都能消费）
└── turtle_trade/
    ├── SKILL.md              策略档案（YAML frontmatter + 条件 + 表现 + 失效场景）
    ├── meta.yaml             机器可读元数据 + 参数快照（用于版本 diff）
    ├── performance.json      历史成功率（回测 + 实盘跟踪）
    └── references/
        ├── conditions.md     条件详解与设计依据
        └── changelog.md      参数版本演进 —— 改参数自动追加
```

### 每个 Skill 记录什么

| 内容 | 说明 |
|---|---|
| 一句话定位 + 设计逻辑 | **为什么这样设计**，而不只是条件罗列 |
| 判定条件 | 逐条列出，与代码一一对应 |
| 参数与来源 | 指向 `config/settings.yaml` 的具体位置 |
| 适用 / 规避的市场状态 | 与市场状态识别联动，回测会验证这个假设是否成立 |
| **已知失效场景** | 经验沉淀（如「退潮期的集体跌停不是错杀」），最有价值的部分 |
| 历史成功率 | 样本外回测 + 实盘纸面跟踪，**两套口径分开记录** |
| 移植来源 | 来自哪个开源项目的哪个文件 |

### 参数变更自动记版本（策略进化的审计链）

`meta.yaml` 保存参数快照，每次 `skills sync` 会做 diff：

```
## v1.0.0 · 2026-09-22 19:11
- 首次建档

## v1.1.0 · 2026-09-22 19:11
- 参数变更：`breakout_window`: 20 → 22
- 变更后表现：样本 1695，胜率 46.4%，次日收盘卖（可实现口径）平均 0.21%
```

### 调参流程（闭环）—— ⚠️ v1.0 冻结期内**不得使用**

> 冻结期内（2026-09-24 ~ 2026-12-31）禁止调参，原因见第 13 章「调参已被冻结」。
> 下列流程是解冻后的操作规范，保留备查。

1. 看 `skills list` 或 `performance.json`，找出判定为 ❌ 无效 / 🟡 观察 的策略
2. 改 `config/settings.yaml` 中对应参数
3. `python -m astock.cli skills sync` → 自动升版本并写入 changelog
4. `python -m astock.cli backtest` → 回测结果自动回填到 `performance.json`
5. 对比 changelog 里的「变更前 / 变更后表现」，决定保留还是回滚

> 判定门槛：样本 ≥ 30 条才算数；胜率 ≥ 50% 且平均收益 > 0 记 ✅ 有效；
> 平均收益 ≤ 0 记 ❌ 无效；收益为正但胜率偏低记 🟡 观察（低胜率高赔率型）。

### API

```text
GET /api/skills               → registry.json（策略索引与判定）
GET /api/skills/{name}        → SKILL.md + meta + performance + references
```

这两个接口**只读文件、不查库**，因此采集/回测期间也能正常访问（与展示层快照同一思路）。

## 十五、v1.0 冻结期：目标与验收

**冻结期：2026-09-24 ~ 2026-12-31。** 期内允许的改动只有三类：修 bug、数据源故障应急、风险类硬约束。

### 三个达成目标（到期对照，不看过程看结果）

| 目标 | 验收标准 | 进度 |
|---|---|---|
| **G1** 影子信号每日自动产出并被结算 | `ads_shadow_pick` 无连续 2 个交易日缺口的信号日 ≥ 95% | 已挂载进 daily，2026-09-24 起算 |
| **G2** 盘中快照积累 | `dwd_intraday_snapshot` 按 (date, slot) 计数 ≥ 60 个交易日 | 2026-09-24 起算 |
| **G3** 影子信号纸面跟踪复现检验结论 | 2027-01 首个复盘日：日度聚类超额 **t ≥ 2 且为正** → 维持；**t < 2** → 降为半仓规则；**≤ 0** → 停用 | 待积累 |

### 停止规则（触发即停用，不进入「再调一版」的讨论）

- 影子信号**滚动 20 日超额 < 0**
- 单日组合回撤 **> 8%**（尾部结构意味着命中失败日会集中亏损）
- 数据链路**连续 3 日**产出失败

### 为什么这一版可以投入使用

- **裁判可信了**：回测口径从不可实现的 `ret1` 换成可实现口径，主链路被诚实判定为无 alpha
  （t=0.09），而不是继续在假目标上调参
- **决策依据有统计基础了**：影子信号是全项目第一个通过**真正样本外**的信号
  （观察期定参 → 验证期 t=3.56）
- **可回测的数据开始积累了**：14:00 快照从零记录 —— 这是「盘中决策」唯一的数据地基，
  且**无法事后补**
- **修改循环被制度终止了**：冻结契约 + 事前写死的验收与停止规则，取代「感觉还能再改进」

> **Phase 2/3 的设想全部暂缓**（LightGBM 排序、状态模型化、参数自动优化、Vue3 界面、
> PostgreSQL 迁移）：在引入新的**有效信息源**之前，模型层再复杂也只是更精细地加工
> 同一批已被市场定价的信息。下一个候选方向是用影子模块的方法论，把尚未使用的数据
> （`dwd_dragon_tiger` 龙虎榜、`dwd_auction` 集合竞价）做成独立影子信号 —— 但**必须等
> 本冻结期的验收结论出来之后**再启动。
